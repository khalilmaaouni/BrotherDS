## 1. The north star chain (docs/NORTH-STAR-CHAIN.md), DECIDED, founder-authoritative 2026-08-15

Verbatim stage order:

    HUMAN INTENT
    DEVELOPMENT METHOD     (Claude native | GSD | BMAD | Superpowers, interchangeable)
    BROTHERMODE            execution provenance
    CHANGE PASSPORT
    BROTHERSBE             behaviour, business impact, risk, required proof,
                            evidence integrity, accountability, release readiness,
                            production observation
    HUMAN DECISION
    RELEASE
    VERIFIED REALITY

Ownership: BrotherMode owns HUMAN INTENT (records goal/scope/success criteria as a project), DEVELOPMENT METHOD (native floor when nothing else installed), EXECUTION (claims, records, done-check, handover, escalation), and produces CHANGE PASSPORT. BrotherSBE owns nothing before the passport, then owns all eight ASSURANCE concerns, consumes the passport, and stops at RELEASE alongside BrotherMode (neither product performs release, "the host does this"). Nobody owns VERIFIED REALITY yet (DOES NOT EXIST per the doc's own status table).

Four UNCONDITIONAL human decision points (RULE ONE, quoted): "Humans stay in the loop at four points: the intent that starts the chain, any forcing condition where guessing is the danger, the release decision, and the acceptance that closes it. A change to either product that removes, bypasses, or silently pre-answers one of those four is refused, whatever it saves."

Status table (as of 2026-08-15, checked against code): CHANGE PASSPORT row reads "DOES NOT EXIST, This is the largest structural gap in the chain", this was true when the chain doc was written; bm_passport.py (the producer half) now exists in code, so as of THIS research pass the passport is BOTH decided and partially implemented (see section 2). Release readiness, production observation, verified reality: all still DOES NOT EXIST.

## 2. The Change Passport, BOTH decided (NORTH-STAR-CHAIN.md) and partially implemented (tools/bm_passport.py)

Five fields, exact wording from docs/NORTH-STAR-CHAIN.md ("The change passport, defined" section):

1. "WHAT WAS DONE: the change identity, its diff range, and the files it touched."
2. "WHO DID IT: the sessions and agents that wrote, the claims they held, and the human accountable."
3. "WHAT WAS RUN: the verifications executed after the last edit, with their results and where they came from."
4. "WHAT WAS NOT ESTABLISHED: the executing side's own honest list of what it did not check." Verbatim continuation: "This field is mandatory and may not be empty, because a passport that claims nothing is unexamined is the lie the whole chain exists to prevent."
5. "WHERE IT CAME FROM: the method used, named but not judged."

Direction of travel (verbatim): "The passport is produced by BrotherMode and consumed by BrotherSBE. It never travels back. Anything the assurance side needs that the passport does not carry is a defect in the passport, not a reason for the assurance side to reach into execution state."

Schema on disk: YES, partially. tools/bm_passport.py is the PRODUCER of a JSON deposit at `<root>/.sbe/passport.json`. It is not a formal schema file (no JSON Schema/.proto); it is a Python script that writes a plain JSON dict. Confirmed live example read from /Users/khalil.maaouni/Documents/BrotherModeUp/.sbe/passport.json:

    {
      "whatWasNotEstablished": [...],
      "whereItCameFrom": "BrotherMode",
      "whoDidIt": [...]
    }

Critically: bm_passport.py only owns/writes THREE of the five fields, `whoDidIt`, `whereItCameFrom`, and `whatWasNotEstablished` (its own gaps only). Fields 1 (`whatWasDone`) and 3 (`whatWasRun`) are NOT produced by this tool and are ABSENT from the live deposit, the tool's docstring says explicitly it "owns exactly two of the five fields the chain names... A third field rides along." So the passport-as-implemented is a partial producer, not the full five-field object.

Hollow-value rule (exact, load-bearing for any consumer BrotherDS writes): "An empty string, a whitespace-only string, an empty list, or null all read as absence on the consuming side. A field this tool cannot establish honestly is OMITTED from the deposit, never padded with an empty placeholder to look filled." Implemented as `_answered()`: None/blank-string/empty-list-or-dict = not answered; 0 and False DO count as answered.

Exit codes (load-bearing contract): 0 = deposit written (whatever it could/couldn't establish); 1 = deposit could not be written to disk; 2 = usage error or NO-DATA (no project root resolvable).

Isolation rule for any third product: "This tool writes <root>/.sbe/passport.json and reads NOTHING under .sbe/: no tasks.json, no evidence/, no existing passport.json... Reaching across the seam to fill a field is the exact failure the seam exists to prevent." Its only inputs are bm_store.py's own store (read-only), `git config user.name`, and --accountable/--method flags.

## 3. The work record and its lifecycle, BOTH decided (docs spec) and code-enforced

Source of truth per its own docstring: docs/specs/canonical-project-protocol.md (FOUND as referenced, not independently read this pass); brotherme/core/schema.py restates it and a test (tools/test_bm_schema.py) asserts the two cannot drift.

Ten states, exact list from brotherme/core/schema.py line 43-54:
`planned, ready, active, blocked, "awaiting review", verified, accepted, delivered, monitored, closed`

`FORBIDDEN_STATE = "done"`, refused by name outright: "the canonical protocol says Done is not a valid state."

LEGAL_TRANSITIONS (exact, schema.py:66-77):
    planned -> ready
    ready -> active
    active -> blocked | "awaiting review"
    blocked -> active
    "awaiting review" -> verified
    verified -> accepted
    accepted -> delivered
    delivered -> monitored
    monitored -> closed
    closed -> (none, terminal)

`closed` is terminal: no move out, forward or backward, with or without a reason (schema.py transition()). Backward moves elsewhere are legal but require a non-empty `reason` string, enforced at the `transition()` call.

BIRTH_STATES (tools/bm_project.py:186): only `planned` or `ready` may be a task's starting state, a deliberately narrower rule than the transition table, "because deriving it would mean a new state added to the lifecycle silently becomes a legal birth state."

Storage: SQLite store at `<root>/.brothermode/store.sqlite3`, accessed via tools/bm_store.py. The `tasks.status` column itself is plain TEXT with NO CHECK constraint in the DB, the ten-state enforcement lives in Python (schema.py's transition()), not in a SQL CHECK. (Contrast: the separate `records` table, used for file claims/fences, DOES have a DB-level CHECK: `state IN ('active','parked','complete','adopted')`, bm_store.py line 1920. Do not confuse the two: `records` = fence/claim state, `tasks` = work-item lifecycle state.)

Done-check, mechanically (references/definition-of-done.md, 15-point checklist; point 8 restates the safety floor): "Verification runs after the final edit, not before it" and "no completion claim without a verifying command run after the last edit, quoted." SKILL.md's safety floor: "Never claim done without a verifying command run AFTER the last edit, quoted."

Fence-close evidence block (references/fences.md, exact): "A fence CLOSES only with an evidence block inline in the registry: the exact command run and its last lines."

## 4. The claim/fence mechanism (references/fences.md + tools/bm_fence_hook.py, 1147 lines, not fully read)

File format: fence lines live in STATE.md (the fence registry), written BEFORE an agent launches, never after ("FENCE THEN DISPATCH, never the reverse").

Five-field contract per fence, exact: "objective, output format, tool guidance, boundaries, termination condition" plus files, agent id, session id, timestamp, declared tier, and a runnable done-check.

One-writer rule: "One writer per file, ever." Enforced by tools/bm_fence_hook.py as a Claude Code `PreToolUse` hook that "refuses a write to a file ANOTHER active claim covers, when installed" (SKILL.md safety floor section). Fails OPEN by default (unclaimed path allowed unless `BM_FENCE_STRICT=1`); does NOT gate Bash, so a shell write bypasses it undetected until later. `BM_FENCE_MODE=enforced` makes a failed check refuse instead of default-allow.

TTL: explicitly NONE by design. Verbatim (references/fences.md): "there is deliberately NO time-based expiry, because a law promising a lease that expires while no code expires anything is worse than no law: a fence is released by an explicit park, complete, adopt, or transfer, and a dead session's fence is ADOPTED at close by the orchestrator, never by a clock."

Valid stage names bm_idle.py knows (tools/bm_idle.py CHAIN_STAGES, lines 90-105, these are the north-star CHAIN stages, distinct from the ten task-lifecycle states above): `intent, method, provenance, passport, behaviour, business-impact, risk, required-proof, evidence-integrity, accountability, release-readiness, production-observation, human-decision, verified-reality`. Note: `release` is deliberately absent, "the host does that, both products stop at the pull request, so no queue item can serve it." An item naming an unrecognized stage is a hard error (NO-DATA), not a silent pass.

What bm_idle.py checks overall: whether a project's queue (`docs/plan/QUEUE.json`) has enough `queued`-state depth to avoid the machine going idle unattended; each item's `state` must be one of exactly `queued, in_flight, done, blocked` (a DIFFERENT, smaller state set than the task lifecycle above, this is queue-item state, a third distinct vocabulary in this codebase). `blocked` items never count toward depth.

## 5. The extension surface, how a third product plugs in

No plugin point exists. Everything found is EDIT-CORE, not register-and-go:

- To add a new CHAIN STAGE (e.g. a BrotherDS-owned stage): edit `tools/bm_idle.py`'s `CHAIN_STAGES` tuple (line 90) AND `docs/NORTH-STAR-CHAIN.md` itself (the chain diagram and ownership table), since NORTH-STAR-CHAIN.md states it is founder-authoritative and CHAIN_STAGES is explicitly sourced from it ("An item may name the stage it serves... The stages of the founder's north-star chain").
- To add a passport field or a new producer/consumer leg: edit `tools/bm_passport.py` directly (it is a single-purpose script, not a plugin-loaded module) plus the spec doc that governs the contract, `docs/specs/2026-08-15-change-passport-seam.md`, which is stated to live in the BrotherSBE repository, not here. A third product wanting to deposit its own passport data would need either (a) its own producer script writing to a different key of `.sbe/passport.json` under a negotiated contract, or (b) a change to bm_passport.py itself to add a third owner. Nothing in the code discovers producers dynamically.
- To add a new work-item lifecycle state: edit `brotherme/core/schema.py`'s `STATES` and `LEGAL_TRANSITIONS`, AND `docs/specs/canonical-project-protocol.md` (source of truth), because `tools/test_bm_schema.py` asserts the two never drift, a schema-only edit without the doc edit fails that test.
- The closest thing to a routing/plugin table that DOES exist: `tools/toolkit_routes.json`, read by `tools/bm_toolkit.py route`. It is explicitly "FOUNDER-EDITABLE BY DESIGN... this file, present and valid, REPLACES the module's embedded default entirely." This is a real, JSON-file extension point, but it routes TASK CLASSES to CAPABILITIES (e.g. "which installed tool handles TDD"), not chain stages or passport fields. A third product could plausibly register itself as a routed capability here without editing bm_toolkit.py's Python, which makes it the one genuine plugin surface found.
- `agents/` (builder.md, fast-worker.md, navigator.md, researcher.md, reviewer.md): the six capability profiles' native invocation surface (references/profiles.md section 3). Adding a BrotherDS-specific capability profile (e.g. "Data Scientist") is not supported by the current fixed six-profile enum in references/profiles.md; it would require amending that reference file plus the delegation ladder in references/delegation.md.

## 6. Terminology law (references/terminology.md)

Core rule, exact: "the user never needs the internal terms below to use this product. In every user-facing sentence, use the plain wording in the right column. The internal term may appear only when the user has explicitly asked for the advanced view."

Three working rules, exact:
1. "Plain wording is not a euphemism. It must state the same fact." (example given: "only one worker edits a file at a time" is the whole truth of the fence.)
2. "When a user asks what a plain phrase means, explain it in one sentence, still without the internal term, unless they ask for the machinery itself."
3. "Advanced view is opt-in per request, never sticky by assumption. After answering an advanced question, the next default output returns to plain wording."

Relevant existing mappings BrotherDS should reuse rather than invent new plain-language for the same concepts: fence/file claim -> "only one worker edits a file at a time"; work record -> "task history"; receipt -> "your recorded approval"; evidence class -> one of four labels: "verified by command", "measured", "verified by inspection", "my reasoning, not verified"; alert rung -> one of four labels: "needs you", "at risk", "for info", "settled".

## 7. Effort/tier system, safety floor, caps (<=6 lines)

Six capability profiles (never hard-coded model names): Navigator, Builder, Reviewer, Fast Worker, Vision Worker, Researcher (references/profiles.md). Three declared tiers per brief: T1 simple fact-find (1 session, 3-10 tool calls), T2 scoped comparison/fix (2-4 subagents, 10-15 calls each), T3 full audit (10+ subagents, fenced scopes), every dispatch must name its tier and reason, or it is logged as a compliance failure (references/delegation.md). Concurrency caps: 1 writer per fence, max 3 live fences in a shared tree, max 3 concurrent agents when builds involved, 6 for read-only fleets, exactly 1 full test suite and 1 GUI driver at a time. Safety floor (SKILL.md, unconditional whenever any write occurs): git status first; one writer per file (bm_fence_hook.py); fence THEN dispatch; never claim done without a verifying command run after the last edit, quoted. Unattended-run ceiling: 8,000,000 output tokens/run, soft stop at 80%, hard stop at 100%; interactive sessions target 2,000,000.

## Top 3 things that would break BrotherDS if ignored

1. **The passport is only 3/5 fields implemented, and BrotherDS cannot fill the gap by reading BrotherMode's internals.** `whatWasDone` and `whatWasRun` are ABSENT from `bm_passport.py`'s actual output today (only whoDidIt, whereItCameFrom, whatWasNotEstablished are produced). If BrotherDS needs "what was done" or "what was run" data, the rule is explicit: that is "a defect in the passport, not permission to reach into execution state." BrotherDS must either wait for BrotherSBE/BrotherMode to complete the producer, or negotiate its own passport-consumer contract rather than parsing `.brothermode/store.sqlite3` directly.
2. **Three separate, easily-confused state vocabularies coexist in this codebase**, and reusing the wrong one silently corrupts data: (a) the ten-state TASK lifecycle (`planned...closed`, Python-enforced in schema.py, no DB CHECK), (b) the four-state CLAIM/fence lifecycle (`active/parked/complete/adopted`, DB CHECK-enforced in bm_store.py), (c) the four-state QUEUE-ITEM lifecycle (`queued/in_flight/done/blocked`, checked by bm_idle.py). None of these three is the CHAIN_STAGES list either (a fourth vocabulary: `intent, method, provenance, passport,` etc.). BrotherDS needs its own clearly-named fifth vocabulary if it adds lifecycle states, not reuse of any existing enum by string-matching.
3. **There is no plugin/registration point for a third product to add a chain stage or a capability profile.** Every extension found requires editing core files directly (`tools/bm_idle.py` CHAIN_STAGES + `docs/NORTH-STAR-CHAIN.md`; `brotherme/core/schema.py` + `docs/specs/canonical-project-protocol.md`; `references/profiles.md` + `references/delegation.md`), each paired with a doc file asserted (by test, in the schema case) to never drift from the code. The only genuinely data-driven, edit-without-code extension point is `tools/toolkit_routes.json` (task-class -> capability routing), which is narrower in scope than what BrotherDS likely needs (registering a whole new chain stage or passport-consumer role).

## The 5 reusable mechanisms BrotherDS should borrow rather than rebuild

1. **The five-field Change Passport contract and its hollow-value rule** (`_answered()`: None/blank/empty = absent; 0/False = real), reuse the definition verbatim rather than inventing a third notion of "field is present."
2. **The done-check discipline**: no "done" claim without a verifying command run after the last edit, with output quoted, enforced by convention + reference file (references/definition-of-done.md), not by a magic tool, cheap to adopt as-is.
3. **The one-writer fence mechanism and its explicit no-TTL/adopt-at-close design** (references/fences.md), directly reusable if BrotherDS has multi-agent writers on shared files.
4. **The capability-profile routing language** (six profiles: Navigator/Builder/Reviewer/Fast Worker/Vision Worker/Researcher, mapped per-runtime, never hard-coded model names), reuse the profile names and the "never hard-code a model version" rule.
5. **The terminology-map pattern itself** (internal term -> single plain-language row, opt-in advanced view), reuse the mechanism (a maintained table gating all user-facing copy), not necessarily the specific rows, for BrotherDS's own jargon.
